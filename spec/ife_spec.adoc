== Introduction

=== Purpose

// Narrative carried from the ratified v1.0 specification.
The Iris Digital Slide file structure specification defines a portable
serialization format for digital pathology whole slide image (WSI) pixel data
and metadata: a highly performant binary structure amenable to massively
multi-threaded encoding and immediate multi-threaded random access; a
dynamically defined file layout that delegates information ordering to the
encoder, allows optional data-blocks and unobtrusive file updates, and
provides complete bi-directional file and encoder version compatibility; and
a secure format that validates structures, prevents file-bound and buffer
overflow violations, and recovers the file structure if header metadata is
corrupted.

[[ife-resources]]
=== Official Implementation and Resources

This specification is published as a *machine-readable schema* rather than as
prose alone. Three JSON documents state the format's identity, its byte
structure, and its enumerated values; every layout table and value table in
this document is generated from them, so a table here cannot disagree with the
schema an implementation is built against.

Implementers *should* consume the schema rather than transcribe the tables in
this document. A reference implementation is published from the same schema at
the address below, and may be consumed in any of the following forms:

* *Header-only.* Define `IFE_HEADER_ONLY` before including the generated
  block header; the definitions fold in and nothing needs linking. Appropriate
  where the byte layer should inline.
* *Static library.* Linked into an application at build time.
* *Shared library.* Dynamically linked, exporting the semantic API — file
  validation, structure abstraction, file mapping and recovery. The generated
  byte layer is deliberately not exported; it is reached header-only.
* *WebAssembly.* The same sources compile under Emscripten, with remote byte
  ranges fetched on demand rather than memory-mapped.


The schema, the reference implementation, this document's sources, and the
release artefacts are all available at:

{repository}[IrisDigitalPathology/Iris-File-Extension]

Two projects implement this specification, and they divide by layer and granularity. The reference implementation, below, provides the byte structure and its validation: the blocks, offsets and values this document defines. The Iris Codec Community Module builds on it and provides image compression, decompression and a high-level slide API:

https://github.com/IrisDigitalPathology/Iris-Codec[IrisDigitalPathology/Iris-Codec]

Implementers writing an encoder or decoder want the schema and the reference
implementation. Implementers who simply need to *open* a slide want the Codec
module. Each publishes bindings for its own layer, so a caller works at the
level the task requires rather than at the level a language binding happens to
expose. The reference implementation presently builds {cpp}; bindings that
expose this layer to other languages are published alongside it as they become
available.

=== Definitions

[[ife-terms]]
==== Terms

The use of "*shall*" indicates a mandatory requirement within the standard.
Deviation from "*shall statements*" violates the standard.

The use of "*should*" indicates an optional but suggested method for
information formatting. Adhering to "*should statements*" may reduce future
re-formatting for compliance, ensures non-explicitly defined requirements are
intuitively defined, and follows good practice.

The use of "*may*" indicates optional implementation and/or formatting without
explicit requirements. Such statements should be implemented if contextually
relevant circumstances arise but use or lack thereof does not explicitly
violate the standard.

The use of the term "*implementation*" or "*implementations*" shall refer to
computer code, either source code or machine code, with the capacity to execute
computational tasks in a way that adheres to this standard.

The use of the term "*offset pointer*" or "*offset*" shall refer to an unsigned
64-bit integer value corresponding to the number of bytes from the start of
file (SOF) towards the end of file (EOF) that the first byte of a file
structure element (<<ife-file-structure-elements>>) is located.

The use of the term "*slide tile*" or "*tile*" shall correspond with a square
sub-image comprising one or more color channels in a compressed or
uncompressed format. The edge length of that square is the *tile size*, given
by TILE_TABLE.TILE_SIZE (<<ife-tile-table>>) and 256 pixels unless a file
states otherwise, so a tile is an array of 65,536 pixel values by default.

The use of the term "*slide layer*" or "*layer*" shall correspond with a series
of slide tiles that comprise a view of a whole slide image at a single defined
magnification (scale). When arranged in a listed format of _N_ length, layers
shall be arranged from lowest resolution (scale), index 0, to greatest
resolution (scale), index _N_ − 1.

NOTE: This layer arrangement is opposite to the layer arrangements in some
contemporary API at the time of publication, such as OpenSlide. The IFE was
designed from the perspective of integration with viewer systems, which will
display the lowest-resolution layer first.

The use of the term "*magnification*" shall differ from the term "*scale*" in
that magnification shall refer to the true microscopic optical magnification
whereas scale shall refer to the relative resolution of layers to a standard
base resolution. The magnification shall be related to the scale as the product
of the scale with an empirically derived scaling coefficient.

The use of the term "*slide space*" or "*fractional tile location*" shall refer
to a horizontal (_X_) and vertical (_Y_) floating point (decimal) spatial axis
that can be used to define a location within a rendered slide that is layer
independent. The value along an axis shall be defined as the pixel location at
the *highest-resolution* layer (_l~N−1~_) divided by the tile size to give the
decimal number of highest-resolution layer tiles such that a location or size
(_x_, _y_) in *slide space* ranges from ([0, _T~(N−1)x~_], [0, _T~(N−1)y~_])
where the origin (0, 0) is defined as the upper-left of the slide and the point
(_T~(N−1)x~_, _T~(N−1)y~_) is defined as the lower-right of the slide using the
same axis as the global slide indexing scheme (<<ife-tile-offsets>>), layer
_N_ − 1.

NOTE: This differs from IFE 1.0, which referenced the lowest-resolution layer
(_l~0~_). The highest-resolution layer is the reference used by other whole
slide imaging standards, and referencing it means an annotation's coordinates
do not change when a layer is added to or removed from a slide — the base
resolution is a property of the scanned material, whereas the number of
downsampled layers is a property of the encoder. See <<ife-annotations>>.

NOTE: Slide space is a *single-precision float in fractional tiles*, not an
integer pixel count and not a fixed-point pair. Coordinates land on a GPU
unchanged: float is the shader's native type, the 24-bit significand represents
every integer tile index exactly up to 2^24^, and the remainder keeps positional
accuracy of about one hundredth of a pixel on a large slide — finer than the
acquisition it describes. A fixed-point per-pixel encoding — the DICOM-style
choice — would be worse: integer bits must cover the whole slide in pixels,
there is no sentinel value, and the coordinates still need conversion for a
GPU.

=== Technical Requirements

* All multi-byte values *shall* be stored in little-endian byte ordering
  without exception.
* Floating point values *shall* be encoded per the IEEE-754/IEC-559
  standard (f16 half, f32 single, f64 double precision).
* Data-blocks are tightly packed: every parameter's byte offset within a
  block is derived from the cumulative widths of the fields preceding it.
  Encoders *may* place blocks at any byte location within the file
  (alignment padding between blocks is permitted but never required).
* Metadata attribute keys *should* be encoded as ASCII with UTF-8 values;
  DICOM tag-value encoding *shall* follow NEMA character-set requirements.

[[ife-file-structure-elements]]
== File Structure Elements

=== Overview and shared structures

The file is a series of floating, tightly packed data-blocks within a sea of
bytes. Statically sized *header blocks* contain data parameters and offsets
to other blocks, forming the offset-chain; dynamically sized *array blocks*
carry repeated entries or raw byte blobs. Entry into the structure is the
*file preamble* and *file header* at the start of file; every other block is
located exclusively through offset fields.

[[ife-file-preamble]]
==== File Preamble

include::{generated}/layout/primitive_FILE_HEADER.adoc[]

The first eight bytes of every IFE file are version-invariant: their layout
will never change in any future IFE version, so a reader can always identify
an Iris file and select the correct specification before parsing any block.

* The first four bytes of the file *shall* be the magic bytes 0x49726973
  ('Iris') in little-endian order.
* SPEC_MAJOR *shall* encode the major version of the IFE specification to
  which the file conforms. A decoder whose supported major version is less
  than the encoded major version *shall not* attempt to read the file
  structure and *should* report the version mismatch.
* SPEC_MINOR *shall* encode the minor version. A decoder whose supported
  minor version is less than the encoded minor version *shall* read the
  file, restricting itself to the fields defined by its own minor version,
  and *should* surface a warning that later-version content is present but
  inaccessible.
* IFE v1.0 files are distinguished by the two bytes at offset 4 reading
  0x5501 (the v1.0 recovery code position); readers *should* detect
  this pattern and report a v1 file rather than a version mismatch.

[[ife-block-header]]
==== Universal Block Header

include::{generated}/layout/primitive_BLOCK.adoc[]

Every data-block begins with the universal header. The validation field
stores the block's own byte offset, so a reader arriving at offset *x* can
confirm *read(x) = x* before trusting any content; the recovery tag then
confirms the block type. Together they enable computationally trivial deep
validation and corruption-recovery scans.

* The validation field *shall* encode the byte offset, from the start of
  file, of the first byte of the block's universal header.
* The recovery field *shall* encode the recovery code assigned to the
  block type.

[[ife-array-header]]
==== Array Header

include::{generated}/layout/primitive_ARRAY.adoc[]

Every array block begins with the universal block header followed by the
array header. Block-specific header fields, where defined, follow the array
header; entries follow the complete header region.

* The stride *shall* encode the byte size of each array entry at the time
  of encoding, and *shall* be used by decoders for entry iteration
  regardless of the entry size defined by the decoder's specification
  version. This is the mechanism of forward compatibility: future versions
  may expand an entry, and prior decoders skip the appended bytes as padding.
* The count *shall* encode the number of stride-sized entries within the
  array. Byte-blob arrays use a stride of one (1), making the count a byte
  count.

=== Statically Defined Values

include::{generated}/constants/statically_defined_values.adoc[]

Null-type constants indicate an optional data-element is not present and
*should* be used to indicate an unused optional parameter rather than
creating a data-block with zero entries.

[[ife-recovery-codes]]
==== Recovery Codes

include::{generated}/constants/recovery_codes.adoc[]

Recovery codes *shall* be encoded as 16-bit little-endian values. The
numerical recovery sequence co-occurs with the high-entropy byte 0x55
(0b01010101) to avoid spurious matches during recovery routines. Tags are
stable forever once assigned; tags of retired blocks are never reused.

[[ife-image-orientations]]
==== Image Orientations

include::{generated}/constants/image_orientations.adoc[]

These name common rotations of the associated-image ORIENTATION field
(<<ife-images>>). That field encodes degrees as an IEEE half-precision value
interpreted modulo 360, so its domain is continuous and these constants
enumerate nothing: they are the rotations an implementation most often needs,
written out so that each is spelled one way. An implementation *shall not*
reject an orientation for being absent from this table.

[[ife-header-blocks]]
=== Header blocks

[[ife-file-header]]
==== File Header

include::{generated}/layout/FILE_HEADER.adoc[]

The file header is the root of the file structure and the only block with a
statically defined location.

* The file header block *shall* begin at byte offset 8, immediately
  following the file preamble (its validation field therefore always encodes
  the value 8).
* FILE_SIZE *shall* encode the size of the file in bytes, identical to the
  value returned by an operating system file-size query, at all times other
  than during active encoding. Validation *shall* fail, and file recovery
  is indicated, when the encoded file size differs from the
  operating-system-reported size. During encoding, this slot serves as the
  atomic write-head (stream cursor) for lock-free space reservation and is
  sealed to the final file size when encoding completes.
* FILE_REVISION *shall* be incremented each time a file modification has
  occurred.
* TILE_TABLE_OFFSET *shall* contain a valid offset to the tile table
  block; it *shall not* be NULL_OFFSET.
* METADATA_OFFSET *shall* contain a valid offset to the metadata block
  even if no optional metadata elements are encoded; it *shall not* be
  NULL_OFFSET.

[[ife-tile-table]]
==== Tile Table

include::{generated}/layout/TILE_TABLE.adoc[]

* ENCODING *shall* be one of the tile encoding values
  (include::{generated}/constants/tile_encodings.adoc[]), excluding the undefined value (0).
* FORMAT *should* describe the pixel channel ordering and bits per channel
  (include::{generated}/constants/pixel_formats.adoc[]); it *may* encode the undefined value (0)
  when the original encoding information is unavailable.
* CIPHER_OFFSET *shall* be NULL_OFFSET unless the tile encoding is
  TILE_ENCODING_IRIS.
* TILE_OFFSETS_OFFSET *shall* contain a valid offset to the tile offsets
  array.
* LAYER_EXTENTS_OFFSET *shall* contain a valid offset to the layer extents
  array.
* TILE_SIZE *shall* encode the edge length in pixels of the square tiles the
  slide is divided into. A value of zero, and the field's absence in a file
  written under 1.0, *shall* both denote 256.

[[ife-tile-size]]
===== Tile Size

Every tile in a slide is the same size, and that size sets the axis of the
global tile indexing scheme and of slide space (<<ife-terms>>). It is a
property of the whole slide rather than of a layer: layers differ in how many
tiles they hold, never in how large a tile is.

Encoders *should* use 256. The field exists so a slide tiled otherwise can be
described rather than misdescribed, not to invite the choice. 256 is what
every IFE file written to date uses, what decoders are tuned for, and what a
reader that ignores this field will assume; a slide that departs from it is
correct but is taking on compatibility risk that the format cannot remove.

NOTE: A 1.0 reader does not read this field and will assume 256. A file that
sets it to anything else is therefore readable by a 1.0 decoder but will be
rendered wrongly by one — unlike PLANES (<<ife-focal-planes>>), where the
1.0 assumption stays true. This is the one place in 1.1 where the appended
field carries meaning a prior decoder needs.

[[ife-cipher]]
==== Codec Cipher

include::{generated}/layout/CIPHER.adoc[]

The codec cipher is a reserved data-block for future use in the Iris Codec.
Its offset in the tile table *shall* be encoded as NULL_OFFSET when unused.

[[ife-metadata]]
==== Metadata

include::{generated}/layout/METADATA.adoc[]

* The codec version entries *should* correspond with the major, minor, and
  build numbers of the Iris Codec implementation that wrote the slide file;
  they *may* be zero if an Iris Codec module, or derived tool, did not
  write the file.
* ATTRIBUTES_OFFSET *should* point to a valid attributes block and

* ANNOTATIONS_OFFSET *may* point to an annotations array and *shall* be

* CLINICAL_OFFSET *may* point to a clinical metadata block
  (<<ife-clinical-metadata>>) and *shall* be NULL_OFFSET if no clinical
  metadata is encoded.
* MICRONS_PLANE *should* encode the physical distance in microns between

  slide is not Z-stacked or the spacing is unknown.
* MICRONS_PIXEL *should* encode a floating point coefficient describing
  the number of microns of physical space each pixel occupies, normalized to
  relative layer scale 1, and *may* encode zero (0.f) if no value is

* MAGNIFICATION *should* encode a floating point coefficient that converts

[[ife-attributes]]
==== Attributes

include::{generated}/layout/ATTRIBUTES.adoc[]

* FORMAT *shall* be one of the metadata format values
  (include::{generated}/constants/metadata_formats.adoc[]) and *should* name
  the discipline the pairs actually follow rather than the undefined value (0).
* VERSION *should* encode the version of the standard FORMAT names — the Iris
  Interoperability Specification version for METADATA_I2S, the encoding year
  for METADATA_DICOM — and *shall* encode zero (0x0000) where that standard
  has no version.
* SIZES_OFFSET *shall* encode a valid offset to the attribute sizes array.
* BYTES_OFFSET *shall* encode a valid offset to the attribute byte array.

The IFE is not intended to validate clinical interoperability metadata
specification conformance; that is outside the scope of this specification.

IFE 1.1 draws the metadata boundary by which block a fact is written into.
What the tissue is and whose it is goes in the clinical metadata stream
(<<ife-clinical-metadata>>). How the image was made — the instrument, the
optics, the stain — goes in these arrays, as does anything else an
implementation wishes to record.

FORMAT states that a file keeps to that boundary. METADATA_I2S is a claim
about what these arrays do *not* contain as much as about what they do: it
undertakes that every pair is a fact fixed when the slide was scanned and that
nothing clinical or identifying was recorded here. That undertaking cannot be
read off the keys, because it concerns the ones that are absent — a slide with
no patient name looks the same whether the name was excluded by discipline or
never existed. So it is declared rather than inferred, and a consumer deciding
whether these arrays are safe to keep reads one field instead of walking every
key against a list of the identifiers it can think of.

The two differ in more than subject, and the difference is the reason they are
kept apart. Acquisition facts are fixed when the slide is scanned and identify
no patient; clinical facts change for as long as the patient has a record, and
disclose a great deal. A slide is therefore de-identified by dropping the
clinical stream — setting CLINICAL_OFFSET to NULL_OFFSET — with no pixel
rewrite and no re-encode, and the scanner, objective and stain survive that
operation. They must: the pixels cannot be interpreted without them and they
disclose nothing.

NOTE: These arrays are deliberately untyped. A field earns a typed slot in
this specification by changing what a decoder does, and nothing here does —
a serial number, a numerical aperture and a scan date are read and displayed,
not acted upon. Recording them as key-value pairs also avoids restating
vocabularies that already exist: the equipment attributes of DICOM PS3.3 are
flat tag-value pairs that these arrays carry as they stand.

The names and admissibility of those pairs are specified separately, by the
Iris Interoperability Specification (I2S), which states that a key is a DICOM
keyword, gives the grammar for flattening DICOM's nested sequences into flat
keys, and defines which facts may be recorded at all. This specification
governs where the bytes are and takes no view on what they say; a file whose
attributes follow no vocabulary is structurally valid and interoperably
useless.

[[ife-layer-extents]]
==== Layer Extents Array

include::{generated}/layout/LAYER_EXTENTS.adoc[]
include::{generated}/layout/LAYER_EXTENTS_entry.adoc[]

* The number of layers *shall* be greater than zero.
* X_TILES / Y_TILES *shall* encode the number of tiles in the horizontal /

* SCALE *shall* have a value greater than zero and any subsequent layer
  *shall* have a scale greater than the previous layer's scale.
* PLANES *shall* encode the greatest number of focal (Z) planes carried by any

  in a file written under 1.0, *shall* both denote a single plane.

[[ife-focal-planes]]
===== Focal Planes

A layer may be Z-stacked: each of its tiles holds several images of the same
field of view captured at different focal depths. Cytology depends on this,
since cells sit at different depths within a preparation and no single focal
plane resolves all of them.

The stack is stored as one byte-stream per tile, not as several. The tile's
OFFSET and SIZE (<<ife-tile-offsets>>) address that stream whole, and PLANES
states how many images it yields. Codecs that predict between frames — AV1
among them — encode a Z-stack far more compactly than the same planes stored
separately, because adjacent focal planes of one field of view differ only
slightly. Recovering the individual planes from the stream is the codec's
business; this specification states only how many are in there.

PLANES is recorded per layer rather than per tile because focal depth is a
property of the acquisition rather than of a position on the slide, and
because a pyramid is normally built from one plane: a Z-stacked slide is
typically stacked at the highest-resolution layer and single-plane above it.
Recording it per layer rather than per tile also keeps the tile offsets array
— by far the largest in the file — at its 1.0 width.

It is a maximum rather than a count so that depth may still vary across a
layer. An acquisition may capture a stack only where there is material to
resolve and a single plane over blank glass, and a tile that is not encoded
at all carries no planes at all. A decoder sizes its buffers from PLANES and
learns what a particular tile actually holds from that tile's stream, which
is the only thing that can answer it: the planes are frames of one encoded
sequence, and how many frames a sequence contains is a question its codec
already answers.

NOTE: A 1.0 reader steps through this array by the stride stored in the array
header and never reads PLANES, so a 1.1 file remains readable to it — every
layer is simply single-plane as far as it is concerned. This is the stride
mechanism of <<ife-array-header>> doing what it exists to do.

[[ife-tile-offsets]]
==== Tile Offsets Array

include::{generated}/layout/TILE_OFFSETS.adoc[]
include::{generated}/layout/TILE_OFFSETS_entry.adoc[]

* The count *shall* equal the total number of global tile indices derived
  from the layer extents array.
* OFFSET *shall* encode the byte offset location relative to the SOF where
  the corresponding compressed tile byte-stream is located and *shall not*
  exceed the 40-bit maximum value (1.0995 TB), or *shall* encode NULL_TILE

* SIZE *shall* encode the number of bytes the compressed tile byte-stream
  consumes and *shall not* exceed the 24-bit maximum value (16.777 MB).

[[ife-tile-pixel-data]]
==== Tile Pixel Data

The compressed tile byte streams referenced by the tile offsets array are
deliberately *not* framed blocks: streams carry no header within the bytes
they occupy, may appear anywhere in the file, in any order (including fully
stochastic order from parallel encoding), and may be interrupted by
intervening data. Each stream is located and sized exclusively by its tile
offsets entry.

* Each compressed byte stream *shall* be comprised of one or more bytes
  encoded according to the encoding algorithm and pixel format encoded in
  the tile table.
* The ordering *may* follow the global tile indexing scheme or *may*
  follow no indexing scheme, arranged in any order the encoder chooses.

[[ife-tile-frame]]
===== The Tile Frame

An encoder *may* precede a tile byte-stream with the __optional__ frame below. Its fields
are placed *backward* from the first byte the tile offsets entry addresses:
the offsets in the table are displacements behind that byte, so VALIDATION
ends exactly where the stream begins and the frame extends towards the start
of file.

include::{generated}/layout/TILE_PIXEL_DATA.adoc[]

The frame sits *before* the addressed bytes rather than within them, which is
what keeps it free. OFFSET and SIZE continue to delimit the codec stream
exactly, so a decoder may still hand those bytes to a codec, or serve them,
without arithmetic — and a decoder written against 1.0, which never looks
behind OFFSET, reads a framed file exactly as it reads an unframed one.

* VALIDATION *shall* encode the byte offset of the VALIDATION field itself,
  which is the address of the stream it precedes less five.
* TILE_INDEX *shall* encode the global tile index of the stream that follows.
* PLANES *shall* encode the number of focal planes the stream carries and
  *shall not* exceed the PLANES maximum of the layer holding the tile
  (<<ife-layer-extents>>).

A frame is detected, not declared: read the five bytes ending at a tile's
OFFSET, and the frame is present when they equal their own position. No field
elsewhere records whether an encoder wrote frames, and none needs to.

Placing VALIDATION adjacent to the stream is what makes that test survive the
frame growing. A future version appends fields at the far end, so the frame's
start moves but VALIDATION does not, and a decoder built against this version
still finds a frame written by a later one — and still reads TILE_INDEX and
PLANES from the displacements stated here. A frame laid out forward from its
start could not offer that: growing it would move the very field a reader
measures to.

NOTE: This is why VALIDATION here is 40 bits rather than the 64 of the
universal block header (<<ife-block-header>>). It is the only structure in
the format that stores its own offset in 40 bits, so a u40 equal to its own
position identifies a tile frame and nothing else — the frame needs no
recovery tag, and does not consume one of the 256 the format has.

The frame exists for recovery, and carries the part of a tile offsets entry
that cannot be worked out from the slide itself: which tile a stream belongs
to. Position alone cannot say, since the ordering above is explicitly free, so
without the frame a scan recovers a heap of streams it is unable to place.

It deliberately does *not* record the stream's length. That is discoverable
from the stream — an AV1 low-overhead bitstream carries a size with each OBU,
and a JPEG terminates at an EOI marker that entropy-coded data cannot imitate,
because every 0xFF within it is followed by a stuffed zero or a restart
marker. Recording a second copy would oblige an encoder to keep the two in
agreement and a decoder to decide which to believe when they disagree.
Determining the extent of a compressed stream is the codec's work, which is
outside this specification; establishing which tile that stream is, is not.
Where the tile offsets array is intact the frame is redundant, and an encoder
that does not want to spend the bytes *should* omit it.

* BYTES_OFFSET *shall* encode the offset of the variable-length image data

* WIDTH / HEIGHT *shall* be greater than zero and less than the 32-bit
  maximum value.
* ENCODING *shall* be one of the image encoding values
  (include::{generated}/constants/image_encodings.adoc[]), excluding the undefined value (0).
* FORMAT *shall* be one of the pixel format values, excluding the
  undefined value (0).
* ORIENTATION *shall* encode the intended degree of rotation as an IEEE
  half-precision float interpreted modulo 360, and *should* encode a value
  < 360. Any degree value is legal; the `ORIENTATION_*` convenience
  constants are listed with the statically defined values in section 2.2.

[[ife-clinical-metadata]]
==== Clinical Metadata

include::{generated}/layout/CLINICAL_METADATA.adoc[]

* The count *shall* be greater than zero and *shall* encode the byte size of
  the contained stream, stored without modification.
* The stream *shall* identify its own format in its leading bytes, and a
  decoder *shall* determine the format from the stream rather than from any
  field of this specification.

This block carries clinical and interoperability metadata that does not
reduce to key-value pairs — a patient, a specimen, a diagnostic report, and
the relationships between them. It holds a whole document, and IFE treats it
the way it treats an ICC profile (<<ife-icc-profile>>): as a byte range
defined by the standard that wrote it, stored verbatim and not parsed here.

IFE 1.1 defines one such stream, *FastFHIR*: a binary encoding of the HL7 FHIR
resource model, whose offsets resolve against the start of the stream and
whose leading bytes record its own magic number, FHIR revision and layout
mode. Nothing about it needs to be restated here, which is the point — the
specification records where the bytes are and stops.

NOTE: This is a different channel from the attributes arrays
(<<ife-attributes>>), not a replacement for them. Attributes remain the place
for flat key-value metadata such as DICOM tag-value pairs, and the metadata
format enumeration describes how those pairs are encoded. A clinical stream
is not a key-value list and takes no value from that enumeration.

IMPORTANT: The METADATA_I2S value of that enumeration named a standard that
was never specified, and no encoder ever wrote it. Implementations *should*
carry clinical metadata in this block. The value itself is retained, and
retains its meaning, because an enumeration value that has been published is
on the wire forever whether or not anything wrote it.

[[ife-annotations]]
==== Annotations Array

include::{generated}/layout/ANNOTATIONS.adoc[]
include::{generated}/layout/ANNOTATIONS_entry.adoc[]

Annotations are positioned and sized at fractional tile locations within the
slide-space convention (<<ife-terms>>), which is measured against the
*highest-resolution* layer.

[IMPORTANT]
====
IFE 1.0 measured slide space against the lowest-resolution layer. The four
coordinate fields keep their position, width and type, so only their meaning
differs and a reader that ignores the version will not notice.

An implementation *shall* interpret `X_LOCATION`, `Y_LOCATION`, `X_SIZE` and
`Y_SIZE` according to the version the file declares (`EXTENSION_MAJOR` and
`EXTENSION_MINOR`, <<ife-file-header>>). Converting a 1.0 file scales each
coordinate by the ratio of the highest-resolution layer's scale to the
lowest's.
====
